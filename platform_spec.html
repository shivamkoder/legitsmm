SYSTEM ARCHITECTURE & ENGINEERING SPECIFICATION

LegitSMM: Platform Structure & End-to-End Working

Decoupled Serverless Architecture, Dynamic Multi-Supplier Failover (MoreThanPanel & NiceSMM), and Atomic Data Flow

LegitSMM is a custom-engineered, automated Social Media Marketing (SMM) reseller platform built to deliver high-retention, non-drop engagement services across YouTube, Instagram, TikTok, Telegram, and other major networks. Rather than relying on monolithic rented scripts or fragile client-side pricing, the platform separates customer-facing Next.js interfaces from asynchronous serverless automation. It enforces double-spend race prevention through PostgreSQL row-level locks, implements automatic multi-supplier failover routing, and verifies non-custodial crypto top-ups directly on-chain, keeping infrastructure overhead near $0/month while scaling seamlessly.

3. Database Ledger Architecture

Every financial movement, upstream catalog item, and fulfillment state is recorded in Supabase PostgreSQL:
  • profiles Table: Stores user identity (UUID linked to auth.users), email, high-precision numeric balance, total_spent, points, referral tracking, and auto-generated reseller API key hashes (api_key_hash).
  • services Table: Contains platform-curated customer-facing offerings with retail rate, min/max bounds, platform category, and quality guarantees. Decoupled from upstream vendor identifiers.
  • service_suppliers Table: Many-to-many routing ledger linking service_id to one or more supplier_id and supplier_service_id entries, storing wholesale cost_rate, priority, and sync availability for automatic failover.
  • supplier_catalog Table: Live mirror of raw vendor catalogs (NiceSMM & MoreThanPanel) with 6,592+ synced services, tracking wholesale price adjustments and supplier-level availability.
  • orders Table: Audits order lifecycles (user_id, service_id, target link, quantity, calculated charge, active supplier_id, supplier_order_id, tried_suppliers array, start counts, remains, and final status).
  • transactions & crypto_deposits Tables: Double-entry financial audit trail enforcing unique idempotency keys and on-chain transaction hashes (tx_hash) to prevent replay attacks and duplicate balance credits.

4. How Background Workers Connect with the Frontend

The frontend never communicates directly with wholesale suppliers. The Supabase database serves as an ACID-compliant bridge between background workers and user-facing Next.js components:

Phase A: Background Catalog Syncing → Dynamic Pricing & Catalog Population

  1. Scheduled Trigger: Upstash QStash dispatches an authenticated HTTP POST request to /api/jobs/sync-catalog. The endpoint verifies cryptographic integrity via verifyQStash(req) to block unauthorized triggers.
  2. Admin Database Access: Initializing createAdminClient() with SUPABASE_SERVICE_ROLE_KEY, the job bypasses Row Level Security to read enabled providers from the suppliers table.
  3. Catalog Ingestion & Margin Calculation: The worker invokes getServices() on MoreThanPanel and NiceSMM APIs, filters invalid items, and executes the atomic apply_catalog_sync SQL procedure. The procedure upserts supplier_catalog, disables dropped services, checks for sudden price spikes (>15%), and automatically recalculates retail rates based on the configured markup (e.g., 21%).
  4. Frontend Rendering: When a user navigates to the storefront, the useServices() hook queries active rows from the services table. React useMemo hooks partition offerings by platform, extract categories, and populate the dynamic OrderForm with real-time limits and rates.

Phase B: Frontend Order Submission → Atomic Dispatch & Failover

  1. Client Validation: The customer configures a service, enters the target link and desired quantity, and submits the form. The frontend computes an indicative quote and dispatches { serviceId, link, quantity, extra } to POST /api/orders.
  2. Database Concurrency Lock: The server retrieves the verified userId from session claims. It invokes the atomic PostgreSQL function place_order, which executes an exclusive row-level lock (SELECT ... FOR UPDATE) on profiles, validates funds against authoritative DB rates, deducts the charge, creates a pending order, and returns active candidate suppliers sorted by cost (cheapest first).
  3. Dynamic Supplier Dispatch & Failover: The backend iterates through the candidate list. It formats a standardized SMM v2 form-encoded action=add request using the selected supplier's API key. If the primary supplier rejects or errors, the router automatically attempts the next candidate supplier without double-billing.
  4. Ledger Commitment: Upon successful acceptance, the backend updates the order record with the returned supplier_order_id and returns confirmation to the UI. If every candidate fails, finalize_order is triggered to instantly cancel the order and issue a full automated refund.

Phase C: Background Status Polling & Automated Refunds

  1. Scheduled Batch Polling: Upstash QStash triggers recurring POST requests to /api/jobs/checkstatus with signature verification, eliminating serverless execution timeouts.
  2. Aggregated Supplier Querying: The worker identifies all active non-final orders (pending, processing, in_progress), aggregates them by supplier_id, and queries live statuses in efficient chunks of 100 via wholesale action=status endpoints.
  3. Automated Ledger Reconciliation & Refunds: Returned statuses are mapped into standard lifecycle states. When an order concludes as completed, the record is closed. If marked canceled or partial, the worker executes the database RPC finalize_order, which calculates the exact undelivered ratio from remains and immediately credits an automated refund back to the user's wallet via apply_transaction('order_refund').
